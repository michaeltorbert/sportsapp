# Schedule diagnostics

Version 1.26.1 adds future-failure capture, not a demonstrated correction or cause for issue #205’s historical HTTP 502. The original response body was lost. Keep #205 open until a supported recurrence provides evidence.

Settings → Support → Schedule diagnostics provides Copy diagnostics, selectable read-only text and Clear diagnostics. Reports stay in one browser-local key, `ss:schedule-diagnostics:v1`. Nothing is automatically transmitted. Copy feedback confirms clipboard acceptance only, not delivery to support. If clipboard permission fails, select the report and use the device Copy command. Clear affects only the diagnostic key. Storage denial falls back to this page’s memory and is disclosed.

Reports use a reconstructed allowlist: ephemeral request IDs, range and request role, client/server side, app version/build commit, absolute incident time, relative stage milliseconds, observed HTTP status, fixed stage/outcome codes, omission count and same-range publication recovery time. Linked client/server records retain their own build and clock; server elapsed times must not be compared as if they were client elapsed times. No raw error text, URL, headers, cookies, provider body, game/team/player data, Duke choices, subscription data or other storage is exported. Malformed optional server diagnostics never reject an admitted board; missing server detail stays explicit, so a hosted 502 alone cannot identify its platform/upstream cause.

Bounds: seven days, maximum 20 incidents and 64 KiB serialized local data, maximum 32 observations per incident. Excess observations preserve the initial causal chain, owned cancellation/deadline origins and latest terminal/final landmarks with an omitted count. Routine recovered fallbacks or cancellations cannot displace terminal/stale failures. Retention and allowlisting are reapplied on read/export. Failure evidence survives later recovery; only a fresh actually published board for the matching date range and scope marks failure recovery. Optional enrichment, another range and canceled refreshes cannot mark recovery. Server evidence is returned as additive metadata and removed before board persistence; no diagnostics enter score caches.

Primary, CDN discovery/requested-week, hosted, parse, validation, cache/stale, owned direct/hosted deadline and hook parent-cancel boundaries are distinguished. CDN shared documents report `reused-or-acquired`, deliberately without an upstream HTTP status: the existing wrapper can return a synthetic 200 for a reused completed document. It does not prove a fresh source request. Generic network rejection remains unclassified; opaque rejection never proves denial. Optional game enrichment is outside schedule acquisition.

A page/platform terminated before JavaScript observes a response cannot reliably capture it. Reports can be lost if browser data is cleared, storage is unavailable and the page closes, or the user opens a different browser. Local reports cannot establish provider-wide availability or reconstruct past failures. No backend, billing, retry, timeout, sound, alert, auth or subscription behavior is changed.

Controlled offline and fixture browser tests exercise production diagnostic and acquisition functions. They are handling evidence, not a reproduction of the historical failure or live provider errors. Actual preview/production verification must admit every ordinary app schedule query, preserve previously stopped direct provider methods, and disclose that hosted-fallback limit. Release still requires exact candidate independent review and normal repository gates; this file is not release evidence.
