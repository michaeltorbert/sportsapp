# Watchlist ordering decisions

This is the cumulative product contract and conflict log. The numeric implementation is documented in [watchlist-priority.md](watchlist-priority.md). Regression coverage lives in [watch-priority.test.mjs](../tests/watch-priority.test.mjs). Repository [AGENTS.md](../AGENTS.md) requires reading and updating this log for every ordering change.

## How to use this record

1. Append the next stable ORD ID for a new instruction. Record the actual wording or faithful paraphrase and date; label uncertain interpretations.
2. Compare against every active rule below. Preserve existing rules unless an explicit new instruction supersedes one. Describe every exception and conflict; ambiguous conflicts need user direction before implementation.
3. Add a test for the requested comparison and run all old and new ordering tests plus the full suite. A failed older test is evidence of a conflict to resolve, not permission to erase it.
4. Add a dated change entry naming the IDs affected, decisions and validation. Commit the log, tests, code and instructions together. Earlier versions and exact code diffs remain in Git history.

## Conflict and supersession history

### 2026-10-09 — ORD-019 hide Duke away games only once play starts

- Source: [issue #123](https://github.com/michaeltorbert/sportsapp/issues/123): “Automatically hide Duke games only when Duke is playing away and the game has actually started.” The aim is to avoid score spoilers while watching an away game on a delay at home. Home games stay visible because the user is likely attending; upcoming games have no score to spoil. Neutral-site games are outside the requested away-only rule.
- Rule: under the automatic default, a Duke game is hidden only when Duke is ESPN's away team, the venue is confirmed not neutral, and play has started. The scheduled kickoff time passing is never enough. Once hidden, the started game stays hidden through the final until the user reveals it.
- Interpretations (assistant, accepted in the reconciled plan, not user wording):
  - Started means the parser's start evidence (period or score above zero, or final) or a live or final status. This covers an in-progress 0–0 game at period 0. A delay before play, or a cancellation or postponement without start evidence, is not started.
  - Before play starts, the newest default applies, even past a delayed kickoff time. A started game uses the default in effect at its scheduled kickoff, which also protects games this device never loaded.
  - The automatic decision is remembered once a game has started and its venue is known. An unknown venue is never remembered, so a visible result is not frozen before metadata can confirm an away game. Missing venue metadata therefore keeps an away game visible unless a manual choice, Always hide or a remembered decision applies; this is a recorded limitation.
- Supersession: ORD-019 supersedes only these ORD-010 clauses: away and neutral-site games hidden by default; unknown home/neutral metadata hidden; and defaults applied by kickoff time to games that have not started. The rest of ORD-010 stays active: per-event hide/reveal independent of future defaults and persisting past final; filtering before category counts, focus links, pinning and Guide; the ORD-007 exception for hidden games only; Duke notifications always off; and ORD-014's record display. ORD-010's text is preserved below as history.
- Storage and migration: preferences move to a v2 key with separate `manual` and `remembered` maps, so new manual choices keep their own provenance and precedence. v1 kept automatic snapshots and manual choices in one boolean map, so no provenance is recoverable. The user approved a one-time reset of those v1 per-game values on 2026-10-10 (UTC): “ok clear them if you need to.” Genuine legacy manual per-game choices may therefore be cleared; this is an accepted exception, not a met preservation requirement. The v1 default timeline (automatic, Always hide, Always show) carries over unchanged. Settings shows a notice in the session where values were cleared. Damaged v1 or v2 data keeps the existing fail-closed Always hide fallback.
- Ordering, ORD-007 pins for visible Duke games, Virginia Tech, alert eligibility and IDs are unchanged.
- Regression: the ORD-019 cases and migration, override, fail-closed and ORD-010/019 integration cases in `tests/duke-visibility.test.mjs`; `tests/browser/duke-visibility.spec.mjs`; updated labels and storage key in `tests/browser/settings-sheet.spec.mjs`. Duke alert exclusion tests are unchanged.

### 2026-09-26 — ORD-015 displayed Upsets use favorite or rank evidence

- Source: [owner clarification recorded in issue #95](https://github.com/michaeltorbert/sportsapp/issues/95#issuecomment-5850305774) after the board refreshed: “An upset is beating either a favored or higher ranked team.” This literal current-task rule is authoritative for display categories and counts. A live, started delayed, or final game qualifies when any trailing validated pregame favorite **or** trailing known higher-ranked team has a score, including a retained valid line favoring the lower-ranked leader or pick’em. When a validated line favors the lower-ranked team, either team's non-tied deficit qualifies: the lower-ranked side by line or the higher-ranked side by rank. This includes unranked non-ACC/SEC betting favorites; without a line or known rank, no unrelated unranked watch is invented. Existing unranked ACC/SEC conference watches remain. Ties and unknown rankings do not invent rank evidence. An actual final counts toward the completed total. Under ORD-011, All is the union of its categories, so a newly qualifying Upsets game also enters All. The original retained-earlier-watch sentence is superseded by ORD-016 for recovered finals.
- Supersession: ORD-015 supersedes ORD-009’s line-first restriction and ORD-012’s line-first display-label interpretation only for Upsets membership, explanation, and counts. It also explicitly supersedes the prior unrelated-unranked-favorite exclusion stated in `docs/watchlist-priority.md` before #95 (“Unrelated unranked favorites do not expand the watchlist to every betting upset”): the user's newer any-favored-team rule includes those games when a validated pregame line establishes the favorite. `gameExpectation` and `gamePriority` continue the accepted ordering policy; phone alert eligibility, IDs, and delivery remain independent. ORD-001–008 and ORD-010–014 otherwise retain their recorded scope.
- Recovery: after kickoff, bounded summary `pickcenter` lookups apply to every scoreboard game without a known pregame line, including unranked non-ACC/SEC matchups. A recovered line still needs the existing structural validation; the lookup does not change ordering or alerts. Live candidates come first; within live and then remaining final/started-delayed candidates, ranked and ACC/SEC games receive first slots. The bounded cache evicts expired, missing-line, and unrelated evidence before retained ranked/ACC/SEC lines, so the broader category does not displace the older watchlist's line evidence under ordinary cache pressure.
